# CLAUDE.md

Conventions for AI agents working in this repository.

## Project

`altarmy-profit` is a local Python tool that finds profitable crafting recipes and production chains for **World of Warcraft: Forever**. Items and recipes come from client DB2 tables (wago.tools CSV exports) loaded into the database (SQLite locally, Postgres for the planned hosted app); auction house prices come from addon scans, CSV or by hand; the engine ranks recipes by profit (buy or craft reagents, then sell via vendor, AH minus the 5% cut, or disenchant). See `README.md` for usage and roadmap.

## Layout

- `src/altarmy_profit/versions.py` – the game versions (`tbc` TBC Anniversary, `forever` WoW: Forever): each `GameVersion` names its `data/<version>/` data files, wago.tools product and pinned build, interface number, WoW flavor folder (`_anniversary_`, `_classic_beta_`), AH cut and postage
- `src/altarmy_profit/db.py` – `Database(url)`: the engine factory (SQLite or Postgres via SQLAlchemy Core), migrated to the newest Alembic revision and `game_versions` and the local user registered on first use; `default_url()` (`DATABASE_URL`, else `data/altarmy-profit.sqlite`); `upsert` (dialect-specific ON CONFLICT), `LOCAL_UID`, build and row-count helpers (settings live in `users.py`)
- `src/altarmy_profit/schema.py` – every table as a Core `Table` on one `MetaData`; `src/altarmy_profit/migrations/` – Alembic env and revisions (`alembic.ini` at the root for the CLI); `tests/test_migrations.py` checks they match `schema.metadata`
- `src/altarmy_profit/auth.py` – `User(uid, tier)`, `LOCAL_USER` (uid `db.LOCAL_UID` = "local", linked), `FREE_TIER_MAX_LEVEL` (30), `user_from_claims` (tier `free` iff the Firebase `sign_in_provider` is `anonymous`), `mode_from_env` (`ALTARMY_MODE`: local | hosted), `FirebaseConfig.from_env`, the `TokenVerifier` protocol and `FirebaseVerifier` (firebase-admin, the `hosted` extra; honours `FIREBASE_AUTH_EMULATOR_HOST`)
- `src/altarmy_profit/users.py` – `ensure_user` (row on first sight, follows tier changes, sets `linked_at`), typed `UserSettings` (selection, `data_version`) and `LocalSync` (local mode's addon paths, mtimes, sync times), each per (user, game version); API keys (`create_key` returns the `ak_…` key once, only its SHA-256 is stored; `user_for_key`, `list_keys`, `revoke_key`)
- `src/altarmy_profit/uploads.py` – uploaded addon files: `ingest` (Alt Army replaces the uploader's characters; Auctionator records every realm with prices, each key resolved alias first, then the uploader's matching character group, then parsed), `scan_time` (file mtime clamped to 30 days), `decompress` (gzip, `MAX_BYTES` 32 MB), `record_upload`/`recent` history, `check_rate` (`RATE_LIMIT` 60/hour)
- `src/altarmy_profit/watch.py` – the CLI watcher (`altarmy-profit watch`, no database): `find_files` (both versions, Alt Army first; `version_of` by flavor folder), `changed` against a JSON state of mtimes, gzipped multipart over urllib (`Transport` injectable), `sync_once`, `run` (backoff; stops on `BadKey`)
- `src/altarmy_profit/legacy.py` – imports older releases' SQLite files (`data/altarmy-profit-<version>.db`, and the pre-versions `data/altarmy-profit.db`) into the database once, as the local user's, then renames them `*.imported`; `cli.main` runs it when `--db` isn't given
- `src/altarmy_profit/ingest.py` – download DB2 CSVs and load one version's game data into the database; `output_count` reads either client's SpellEffect encoding
- `src/altarmy_profit/engine.py` – pure profit/chain logic (no I/O). Every tree `Node` lists its `options` (vendor, ah, `craft:<recipe id>`, cheapest first) and the `option` taken; `Result.sell_options` gives each exit's best profit. `evaluate(recipe, choices)` takes user picks keyed by tree path (`r.0`, `r.0.1`; `sell` for the exit); subtrees with a pick skip the memo
- `src/altarmy_profit/prices.py` – the price store and its sources: auction houses (`find_auction_house`, `auctionator_auction_house`, `unnamed_auction_house`), `record_snapshot` (the one way prices get in; writes observations only for news and moves `price_current`), `record_daily`, `prune`, `load_current`, `auction_houses` (with price counts), `daily`; CSV, manual and Auctionator imports
- `src/altarmy_profit/auctionator.py` – pure parser for Auctionator's SavedVariables (Lua string holding CBOR): per item an `ItemPrice` (latest minimum buyout, per-day `DayStats` high/low/available)
- `src/altarmy_profit/luasv.py` – pure generic parser for SavedVariables files (`Name = <Lua table>` statements); nesting capped at `MAX_DEPTH`
- `src/altarmy_profit/altarmy.py` – pure reader for the Alt Army addon's `AltArmy_TBC.lua`: characters, professions, learned recipe ids (= `recipes.spell_id`); `groups` by realm/faction, `crafters`
- `src/altarmy_profit/store.py` – `load_market(conn, game_version, auction_house_id, ah_cut=, mail_postage=)`: database rows to engine dataclasses; characters and AH blocks per user and version; `search_prices` (by name, optionally only up to a required level)
- `src/altarmy_profit/service.py` – web use-cases (every per-user function takes `user_uid` after `conn`): `MarketCache` (per version, one `Market` per auction house); `search` over the selected realm/faction's characters (`engine.recipes_for_characters`: learned recipes, or with `include_unlearned` every recipe of their professions; chains only sub-craft through those), selling only via the allowed exits and keeping what an `engine.Filters` (min/max cost, profit, ROI) accepts; `evaluate`: one recipe with the user's `choices`; realm/faction `selection` and its auction house (`selected_auction_house`, `pricing_auction_house`); `sync` (local mode only), which re-imports Alt Army characters and records the selected realm's Auctionator scan whenever either file's mtime changes; game data update
- `src/altarmy_profit/api.py` – FastAPI JSON API (`create_app(game_versions, database=..., mode=, verifier=, firebase=)`: one shared `Database`, a market cache and locks per version; tests pass `mode` and a fake `verifier`); also serves the built `frontend/dist`. Dependencies: `CurrentUser` (local: `LOCAL_USER`; hosted: the bearer Firebase ID token, 401 without), `LinkedUser` (403 for free: characters, selection, rank, evaluate, ah-blocked), `LOCAL_ONLY` (404 in hosted: sync, sources, file lookups, game-data update, reload). `Uploader` (upload route only: a Firebase token or an `ak_` API key; local mode ignores both). Public: `/api/config` (mode, Firebase web config), `/api/versions`. `POST /api/uploads` (multipart `file`, `kind`, `modified_at` ms, `via`; plain or gzipped; 400 bad file, 413, 429; every outcome in `uploads`), `GET /api/uploads`; `/api/keys` GET/POST and `DELETE /api/keys/{id}` (LinkedUser). `/api/me`; `/api/realms`; `/api/prices` and `/api/prices/{item_id}` apply the free tier's level gate. Every per-game route takes a required `game_version` query parameter (the `State` dependency); `GET /api/versions` lists them. The front end keeps the chosen version in `lib/gameVersion.ts` (header switch, `GameVersionProvider`) and puts it first in every query key after the route name. `GET /api/status` runs the addon sync in local mode only, and the front end polls it (every 30 s and on window focus); its `data_version` is part of the characters/rank/evaluate query keys. `POST /api/evaluate` re-costs one recipe with the choices the user made in its flow chart (`ResultsTable` holds them per recipe, `lib/choices.ts`; the row then shows the changed plan until Reset). `GET /api/rank` takes `exits` and optional bounds (omitted = unbounded) and returns the first `top` results plus `total`; the Search tab pages through them 50 at a time
- `src/altarmy_profit/cli.py` – argparse command line (`ingest`, `import-prices`, `import-auctionator`, `import-altarmy`, `set-price`, `rank`, `ui`); global `--game-version` (default forever) and optional `--db` (a SQLite file); `ui` runs uvicorn on :8600 serving both versions
- `frontend/` – Vite + React + TypeScript + Mantine + TanStack Query; `components/AuthProvider.tsx` (in `main.tsx`, outside `App`) reads `/api/config`, signs in with Firebase in hosted mode (`lib/auth.ts`, SDK loaded lazily; `api/client.ts` adds the token) and provides `lib/session.ts`'s `useSession()` (local/linked outside a provider, so tests need no auth mocks; `renderWithProviders(ui, session)`); `App` shows tabs by mode and tier (guests: Prices, Upload; hosted linked: Search, Prices, Upload, Manage; local: Search, Prices, Manage); `components/Account.tsx` links an email, signs in, resets a password and signs out (email/password only, no Google); `UploadTab.tsx` (hosted) and `ApiKeysCard.tsx` (hosted Manage); `src/api/schema.d.ts` is generated from the API's OpenAPI spec
- `scripts/export_openapi.py` – writes `frontend/openapi.json` (input for `npm run gen-types`)
- `data/<version>/disenchant.csv` – disenchant results (not in DB2): Forever's hand-filled, TBC's generated by `scripts/build_disenchant.py` from Auctionator's brackets (`src/altarmy_profit/disenchant_rates.py`)
- `data/<version>/vendor_items.csv` – items vendors sell (not in DB2), generated by `scripts/build_vendor_items.py --game-version forever|tbc` from vmangos' (`vmangos.py`) or cmangos' (`cmangos.py`) world database
- `scripts/bench_rank.py` – ranking timings per realm/faction; `scripts/probe_blizzard_api.py` – checks whether Blizzard's API serves Anniversary AH data (needs `BLIZZARD_CLIENT_ID`/`SECRET`)
- `docs/HOSTED_PLAN.md` – the hosted, multi-user plan and Phase 0 findings; `docs/ROADMAP_IDEAS.md` – feature ideas
- `.github/workflows/check.yml` – CI: `check.py`, and pytest against a postgres:16 service
- `firebase.json` – the Firebase Auth emulator (port 9099) for trying hosted mode locally; `.firebaserc` and `hosted.env` – the real project (`alt-army-prod`, public web config), loaded by `npm run dev:hosted` (`scripts/dev-api.mjs --hosted`)
- `tests/` – pytest; `conftest.py` holds the `database`/`conn` fixtures (SQLite, or Postgres with `TEST_DATABASE_URL`), `set_prices`, and a tiny fake DB2 CSV set shared by tests

## Commands

Use the project venv (`.venv`); do not install packages globally. If it is missing: `python -m venv .venv`, then `.venv\Scripts\python -m pip install -e ".[dev,ui]"`. Front-end packages live in `frontend/node_modules` (`npm ci` in `frontend/`); the root `package.json` only holds dev tooling (`npm ci` in the root).

- `python scripts/check.py` – ruff lint, ruff format check, mypy (strict), pytest, then regenerates the OpenAPI spec and TS types and runs oxlint, vitest and `tsc -b && vite build`. **Run before considering any change done.** Pass `--skip-frontend` for Python-only iteration.
- `ruff check . --fix`, `ruff format .`, `mypy`, `pytest` – individual Python tools; `npm run lint|test|build|dev|gen-types` in `frontend/`.
- Postgres: set `TEST_DATABASE_URL` (e.g. `postgresql+psycopg://postgres:postgres@localhost:5432/altarmy_test`) and run `pytest`; the tests drop and recreate that database's `public` schema, so never point it at real data. CI does this on every push.
- Schema changes: edit `schema.py`, then `alembic revision --autogenerate -m "..."` (uses `DATABASE_URL`, else `data/altarmy-profit.sqlite`; point it at a database migrated to head), review the revision (SQLite needs batch operations; `env.py` renders them) and keep `test_migrations.py` green on both databases.
- Dev loop: `npm run dev` in the repo root runs the API (`scripts/dev-api.mjs`, venv python, :8600) and, once it answers, Vite on :5173, which proxies `/api` to it.

## Conventions

- **Money is integer copper** everywhere (prices, costs, profit), including the JSON API. Format only at the display edge: `format_money` in Python (CLI), the `Money` component (`frontend/src/components/Money.tsx`, coin icons) in the front end.
- **User state is per user**: characters, `user_settings`, `local_sync` and `ah_blocked` carry `user_uid`; store/service/users functions take it right after `conn`. The CLI, `legacy.py` and scripts act as `db.LOCAL_UID`. Never gate on mode inside service code: tiers and modes are the API's dependencies.
- **Uploads are untrusted**: on bad input the parsers must only raise `ValueError` (the API's 400); `test_mangled_files_only_raise_value_error` fuzzes them. Never store an uploaded file.
- API handlers are plain `def` (FastAPI runs them in a threadpool) and open their own connection per request (`database.begin()`); never share a connection across threads.
- **Storage is SQLAlchemy Core** (no ORM) against `schema.py`, and must work on SQLite and Postgres: no raw SQLite-only SQL (`INSERT OR REPLACE`, `PRAGMA`) outside `db.py`'s engine setup and `legacy.py`; use `db.upsert`. Functions taking a `Connection` never commit: the caller owns the transaction (`Database.begin()` in the API and CLI; tests use an autocommit connection). Order query results explicitly; row order is not insertion order on Postgres.
- After changing API models or routes, regenerate `frontend/openapi.json` and `frontend/src/api/schema.d.ts` (`check.py` does this) and commit both.
- **Keep `engine.py` pure**: no file, DB or network access. Load data in `store.py` and pass plain dataclasses in.
- **Type annotations are required**; mypy runs in strict mode over `src` and `tests`, and the front end uses TypeScript `strict`.
- Prefer red-green-refactor: write a failing test first, then make it pass. Ingest tests use fixture CSVs, never the network. API tests use FastAPI's `TestClient`; front-end tests use vitest + Testing Library with `fetch` stubbed (`frontend/src/test/utils.tsx`).
- Line length is 110; let `ruff format` handle style.

## Data gotchas

- Local mode keeps **one SQLite file** (`data/altarmy-profit.sqlite`) for both versions, the same schema as Postgres. Game data is keyed by `game_version`; `user_settings` (selection, `data_version`), `local_sync` (addon paths, mtimes), characters and `ah_blocked` by `user_uid` and `game_version`; item and recipe ids are only meaningful within one version. The pinned/loaded build is `game_versions.build`. `recipe_reagents.slot` keeps DB2's reagent order, which the flow chart's choice paths (`r.0`, `r.1`) depend on.
- Disenchant results are server-side loot data and are **not** in DB2. Without a version's `disenchant.csv`, disenchant is ignored. Do not invent drop tables.
- DB2 does not say which vendors sell which items. `data/<version>/vendor_items.csv` (unlimited stock, no condition, no token cost, spawned vendor) says which; the per-unit price is `items.buy_price / items.buy_count` (DB2 `BuyPrice` / `VendorStackCount`), rounded up. The engine buys each reagent from the cheaper of vendor and AH (ties go to the vendor). DB2's `BuyPrice` is set on nearly every item, so it alone does not mean a vendor sells it.
- `recipes.min_skill` currently comes out as 1 for every real recipe, so do not rely on it. Recipe output count comes from `SpellEffect.EffectBasePointsF` and is only spot-checked.
- Item tooltips (`store.load_item_details`, `/api/rank`'s `items` map) use denormalized `items` columns filled at ingest: subclass names from `ItemSubClass`, icon names from `ManifestInterfaceData` (`Interface\Icons` only; the browser loads them from wow.zamimg.com). Stats, armor and weapon damage are not shown: ItemSparse holds only stat allocations. `db.init_schema` adds missing item columns to older databases; they stay empty until the next game data update.
- Re-running `altarmy-profit ingest` rebuilds that version's items, recipes and disenchant rows but leaves prices, users and their characters, settings, `ah_blocked` and the other version alone.
- **Prices are per auction house** (`auction_houses`: version, realm, faction; faction `""` = one shared by both factions, as Forever's `ClassicBetaPvE`; realm `""` = the unnamed one CLI prices use before any characters exist). A selection's auction house is its faction's, else its realm's shared one (`prices.find_auction_house`); an Auctionator key ending in the faction means a split house. Every source records a `price_snapshots` row; `price_observations` get only news (no current price, a later day, or a different price seen no earlier) and move `price_current`, which the engine reads; the newest `seen_at` wins whatever the source, so a manual price holds until a later scan. An Auctionator item was seen at the scan time if its last day is the scan day, else at the start of that day. `price_daily` comes from Auctionator's h/l/a (high = highest minimum buyout that day, low = `l` or else `h`, available = most seen) and is only rewritten from the newest stored day on. Observations older than 90 days are pruned at each sync; snapshots `price_current` points at are kept. Money columns for prices are `BigInteger` (copper exceeds 2^31).
- `ah_blocked` holds items the user never wants sold on the AH (per game version, not per realm; set from a search row's ⋯ menu, listed on the Manage tab, `/api/ah-blocked`). It is passed per request as `Market(no_ah=...)`, which drops only the `ah` exit for those items: they can still be bought on the AH, and disenchant materials are still valued at AH prices. The cached base market never holds it, so toggling needs no cache invalidation.
- Alt Army recipe ids are craft spell ids. On TBC clients one recipe is stored under several alias keys sharing a `primaryRecipeID`; Enchanting rows carry only `color`. Auctionator keys realms as the realm name without spaces, plus the faction where auction houses are split (`ClassicBetaPvE`, `Dreamscythe Horde`); `service.match_auctionator_realm` maps a realm/faction to it, and the key is stored as a `realm_aliases` row. Auctionator's day numbers count from 2020-01-01 in local time; it drops days older than its history setting, and random-suffix gear (`gr:` keys) is skipped.
- Characters and mail: `Market` gets the selected characters as `engine.Crafter`s and costs every craft *at a character* (`Market._obtain`): each reagent is bought there, or crafted by any character who can (learners, or with `include_unlearned` and no learner, anyone with the profession) and mailed over if that is someone else. The final crafter is whichever gives the best profit. Postage is `MAIL_POSTAGE` (30c) per attachment, one stack each (`items.stack_size` from `ItemSparse.Stackable`; older databases read 1 until the next game data update). A disenchant is free if the final crafter enchants, else the output is mailed to the best enchanter; with no enchanter at all the disenchant exit is dropped. Postage is in `cost` and shown as `mail` steps and flow nodes; steps carry `who`. Without crafters (CLI `rank`) one unnamed character does everything, so nothing is mailed. Costs are whole batches (spares from multi-output crafts are not credited).
- The pinned builds are `GameVersion.default_build` in `versions.py`; `ingest.latest_build(product)` resolves the newest build of a wago.tools product (`wow_classic_beta`, `wow_anniversary`) from its `/api/builds/latest` JSON. TBC's SpellEffect leaves `EffectBasePointsF` at 0 and encodes counts as `EffectBasePoints` + a 1..`EffectDieSides` roll. Downloaded CSVs are cached under `cache/` (git-ignored, as is `data/*.db`).
